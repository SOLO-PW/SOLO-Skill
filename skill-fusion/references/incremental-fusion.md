# 增量融合

## 概述

增量融合是在已融合的 Skill 基础上，继续融合新 Skill 的模式。与 full 模式从零开始不同，增量融合以已有融合结果为基准，在其上扩展而非重建。

## 适用场景

- 已完成 A + B 融合，现在要加入 C
- 渐进式构建复合 Skill（先融合核心，再逐步扩展）
- 在已有工具箱中添加新能力模块

## 与 full 模式的差异

| 维度 | full 模式 | incremental 模式 |
|------|-----------|------------------|
| 输入 | 2+ 个原始 Skill | 1 个已融合 Skill + 1 个新 Skill |
| 分析范围 | 所有 Skill 两两交叉 | 仅新 Skill 与基准交叉 |
| 结构设计 | 从零设计 | 在基准结构上扩展 |
| 冲突上下文 | 无先验决策 | 需考虑已有融合决策 |
| 风险 | 融合失败可重做 | 可能破坏已有模块边界 |

## 增量融合流程

### 步骤 1：基准验证

验证已融合 Skill 的完整性：

1. 读取基准 Skill 的 SKILL.md
2. 检查融合日志是否存在且完整
3. 从融合日志中提取：
   - 来源 Skill 列表
   - 已解决的冲突及决策
   - 被排除的能力及原因
4. 验证 references/scripts/assets 结构完整

**验证失败处理**：
- 融合日志缺失 → 警告用户，将基准视为普通 Skill 处理
- 资源引用断裂 → 修复后继续
- 结构严重损坏 → 建议使用 full 模式重新融合

### 步骤 2：新 Skill 解析

对新加入的 Skill 执行标准解析（同 full 模式步骤 2），构建能力画像。

### 步骤 3：增量关系分析

仅在新 Skill 与基准 Skill 之间执行交叉分析：

1. **功能重叠检测** — 新 Skill 的能力是否与基准已有能力重叠
2. **互补性映射** — 新 Skill 能否填补基准的能力缺口
3. **冲突检测** — 新 Skill 是否与基准的已有决策矛盾
4. **边界影响评估** — 新 Skill 是否会破坏已有的模块边界

**关键检查：已有决策兼容性**

```
对基准融合日志中的每个已解决冲突：
  检查新 Skill 的方法是否与已选方案矛盾
  如矛盾 → 升级为严重冲突，需交互式解决
```

**关键检查：模块边界完整性**

```
对基准中的每个模块边界定义：
  检查新 Skill 的能力是否跨越边界
  如跨越 → 评估是否需要重新划定边界
```

### 步骤 4：增量冲突解决

除标准冲突解决流程外，增加：

**回溯冲突**：新 Skill 的方法与基准中已选方案矛盾时：
1. 回顾原始冲突的决策理由
2. 评估是否需要推翻原有决策
3. 如推翻，检查对基准其他部分的影响
4. 向用户说明影响范围，等待决策

**边界冲突**：新 Skill 跨越已有模块边界时：
1. 分析跨越的必要性
2. 评估重新划定边界的成本
3. 提供选项：
   - 选项 A：调整边界以容纳新能力
   - 选项 B：将新能力拆分到对应模块
   - 选项 C：新能力作为独立模块

### 步骤 5：增量结构扩展

在基准结构上扩展，而非从零设计：

**SKILL.md 扩展**：
1. 更新 frontmatter：扩展 description 覆盖新触发场景
2. 扩展 body：在合适位置插入新工作流/模块
3. 更新融合日志：追加增量融合记录

**资源扩展**：
1. `references/` — 添加新 Skill 的参考文件，如与已有参考重叠则合并
2. `scripts/` — 添加新脚本，如与已有脚本冲突则解决
3. `assets/` — 添加新资源，用命名空间前缀避免冲突

**扩展策略**：

| 基准结构 | 新 Skill 关系 | 扩展方式 |
|----------|---------------|----------|
| 单领域深度 | 同领域 | 深度扩展：合并到现有工作流 |
| 单领域深度 | 不同领域 | 广度扩展：新增领域模块 |
| 多领域广度 | 已有领域 | 深度扩展：合并到对应领域模块 |
| 多领域广度 | 新领域 | 广度扩展：新增领域模块 |

### 步骤 6：增量验证

除标准验证外，增加：

- [ ] 基准 Skill 的已有能力未被破坏
- [ ] 已有模块边界未被不当跨越
- [ ] 融合日志完整记录增量变更
- [ ] 新增内容与已有内容风格一致
- [ ] SKILL.md 总行数仍在 500 行以内

**退化检查**：对比增量融合前后的能力覆盖，确保无能力丢失或弱化。

## 增量融合日志格式

在基准融合日志基础上追加：

```html
<!-- 融合日志
来源 Skills: skill-a, skill-b (原始), skill-c (增量)
融合模式: full (原始) + incremental (增量)
已解决冲突:
- [严重] PDF 提取方法 → 用户选择 pdfplumber (原始决策)
- [高] 图片调整算法 → 合并：照片用双线性，像素画用最近邻 (原始决策)
- [中] 数据格式 → 增量：扩展支持 YAML 格式 (增量决策)
保留能力: 全部
排除能力: 无
增量变更:
- 新增能力: YAML 数据格式化 (来自 skill-c)
- 新增参考: references/yaml-format.md
- 修改模块: 数据输出模块 (扩展支持 YAML)
融合日期: 2024-01-15 (原始), 2024-02-20 (增量)
-->
```

## 增量融合的风险与缓解

| 风险 | 说明 | 缓解措施 |
|------|------|----------|
| 能力稀释 | 每次增量融合可能弱化核心焦点 | 每次增量后验证核心能力仍在 |
| 复杂度累积 | 多次增量后 Skill 可能过于复杂 | 3 次增量后建议评估是否需要重构 |
| 决策冲突 | 新 Skill 可能与早期决策矛盾 | 回溯冲突时评估全局影响 |
| 边界模糊 | 多次扩展后模块边界可能模糊 | 定期重新审视和明确边界 |

## 增量融合次数建议

| 增量次数 | 建议 |
|----------|------|
| 1-2 次 | 正常操作 |
| 3 次 | 建议进行一次整体审查 |
| 4+ 次 | 强烈建议使用 full 模式重新融合所有源 Skill |
