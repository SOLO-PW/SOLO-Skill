# 融合示例

## 示例 1: 两个互补 Skill

### 输入 Skill

| Skill | 描述 | 核心功能 | 资源 |
|-------|------|----------|------|
| **pdf-extractor** | 从 PDF 文件提取文本和表格 | 使用 pdfplumber 进行 PDF 文本提取 | `scripts/extract.py`, `references/pdfplumber-guide.md` |
| **data-formatter** | 将提取的数据格式化为结构化输出 | 数据转换和格式化 | `references/format-specs.md` |

### 融合过程

| 阶段 | 操作 | 结果 |
|------|------|------|
| 1-2 | 解析两个 Skill | A 处理 PDF 读取，B 处理输出格式化 |
| 3 | 关系分析 | 无冲突。强互补性：A 的输出是 B 的输入 |
| 4 | 结构设计 | 统一流水线：PDF → 提取 → 格式化 → 输出 |
| 5 | 内容合成 | 合并为带两个阶段的工作流 |

### 融合结果: `pdf-to-structured-data`

```yaml
---
name: pdf-to-structured-data
description: >
  从 PDF 文件提取内容并转换为结构化格式。
  支持文本提取、表格解析，输出为 CSV、JSON 或 Markdown。
  当用户希望将 PDF 数据提取为有组织的机器可读格式时使用。
---
```

```markdown
# PDF 转结构化数据

## 流水线

1. **提取** — 使用 pdfplumber 读取 PDF 内容
   - 参见 [references/pdfplumber-guide.md](references/pdfplumber-guide.md)
2. **转换** — 将原始提取内容转为结构化格式
   - 参见 [references/format-specs.md](references/format-specs.md)
3. **输出** — 写入用户指定的格式（CSV/JSON/Markdown）

## 使用

提供 PDF 路径和期望的输出格式。
```

**关键洞察**：互补 Skill 产生最干净的融合 — 它们自然形成流水线。

## 示例 2: 两个重叠 Skill

### 输入 Skill

| Skill | 描述 | 核心功能 | 约束 |
|-------|------|----------|------|
| **image-resizer** | 调整图片大小并保持质量 | 使用 Pillow 和 Lanczos 重采样调整大小 | 始终使用 Lanczos 保证质量 |
| **image-optimizer** | 优化图片用于网页交付 | 使用 Pillow 调整大小 + 压缩，根据图片类型选择 LANCZOS 或 NEAREST | 像素画用 NEAREST，照片用 LANCZOS |

### 融合过程

| 阶段 | 操作 | 结果 |
|------|------|------|
| 3 | 重叠检测 | 两者都调整图片大小，但策略不同 |
| - | 冲突 | Skill A 始终用 Lanczos；Skill B 用条件重采样 |
| - | 解决 | 交互式 — 用户选择条件分支（策略 4） |

### 融合结果: `image-processor`

```yaml
---
name: image-processor
description: >
  为各种用例调整大小和优化图片。支持保质量调整大小、
  网页优化和格式转换。当用户需要调整大小、压缩或优化图片时使用。
---
```

```markdown
# 图片处理器

## 调整大小策略

- **照片 / 复杂图片**：使用 Lanczos 重采样（最佳质量）
- **像素画 / 简单图形**：使用最近邻（保持锐利边缘）
- **网页交付**：调整大小后，应用压缩（质量 80-85）

用户未指定时自动检测图片类型。
```

**关键洞察**：重叠 Skill 需要冲突解决。条件分支通常产生最佳结果。

## 示例 4: 带资源冲突的 Skill

### 输入 Skill

## 示例 5: 融合失败案例（反模式）

### 输入 Skill

| Skill | 描述 | 核心功能 |
|-------|------|----------|
| **database-migrator** | 数据库迁移工具 | 将数据从 MySQL 迁移到 PostgreSQL |
| **video-editor** | 视频编辑工具 | 剪辑、合并、转码视频 |

### 融合过程

| 阶段 | 操作 | 结果 |
|------|------|------|
| 2 | 领域分析 | 两个完全不同的领域（数据库 vs 视频） |
| 3 | 关系分析 | 无功能重叠，无互补性，无自然流水线 |
| 4 | 范围评估 | 融合将产生跨越 2 个不相关领域的 Skill |

### 建议

**不要融合**。这些 Skill 应该保持独立。

**原因**：
- 无共享领域知识可合并
- 无工作流可整合
- 融合后的 Skill 将违反单一职责原则
- 用户不太可能同时需要这两个功能

**替代方案**：
- 保持两个 Skill 独立
- 如用户需要两者，分别调用
- 考虑创建第三个 Skill 来编排这两个 Skill（如果需要组合工作流）

**关键洞察**：不是所有 Skill 都应该融合。当 Skill 属于完全不相关的领域时，保持它们独立。

## 示例 6: 低交叉度但高融合价值（场景串联）

### 输入 Skill

| Skill | 描述 | 核心功能 | 领域 |
|-------|------|----------|------|
| **data-cleaner** | 数据清洗工具 | 处理缺失值、异常值、格式标准化 | 数据处理 |
| **data-visualizer** | 数据可视化工具 | 生成图表、仪表盘 | 数据可视化 |

### 交叉度分析

| 维度 | 分析结果 |
|------|----------|
| 功能重叠 | <10%（清洗 vs 可视化，完全不同） |
| 领域关系 | 相邻领域（数据处理 → 数据展示） |
| 数据流 | A 的输出（清洗后数据）是 B 的输入 |

### 深度分析发现

**场景串联价值**：
- 用户典型工作流：获取原始数据 → 清洗 → 可视化 → 分享
- 当前痛点：需要分别调用两个 Skill，手动传递数据
- 融合价值：形成"清洗+可视化"一键完成的连贯体验

**决策**：深度整合（场景串联型融合）

### 融合结果: `data-pipeline`

```yaml
---
name: data-pipeline
description: >
  端到端数据处理流水线：从原始数据到可视化图表。
  自动执行数据清洗、转换和可视化，支持多种图表类型。
  当用户需要快速将原始数据转换为可分享的图表时使用。
---
```

```markdown
# 数据流水线

## 快速开始

提供原始数据文件，自动完成清洗和可视化：

```
原始数据 → [数据清洗模块] → [可视化模块] → 输出图表
```

## 模块边界

- **数据清洗模块**（来自 data-cleaner）
  - 职责：处理缺失值、异常值、格式标准化
  - 边界：输出清洗后的结构化数据

- **可视化模块**（来自 data-visualizer）
  - 职责：根据数据特征生成合适图表
  - 边界：接收清洗后的数据，不处理原始数据

## 使用示例

### 场景 1：快速可视化（默认）
自动选择最佳图表类型，一键生成。

### 场景 2：自定义清洗 + 自动可视化
指定清洗参数，可视化模块自适应。

### 场景 3：仅清洗 / 仅可视化
单独调用各模块（保留原子能力）。
```

**关键洞察**：低交叉度不等于低融合价值。通过深度理解用户场景，发现"场景串联"价值，实现有意义的融合。

## 示例 7: 增量融合

### 背景

已融合 Skill `data-pipeline`（来自示例 6：data-cleaner + data-visualizer），现在要加入新 Skill `data-exporter`。

### 输入 Skill

| Skill | 描述 | 核心功能 | 领域 |
|-------|------|----------|------|
| **data-pipeline**（基准） | 端到端数据处理流水线 | 数据清洗 + 可视化 | 数据处理 |
| **data-exporter**（新增） | 数据导出工具 | 导出为 CSV/Excel/JSON/PDF | 数据输出 |

### 增量融合过程

| 阶段 | 操作 | 结果 |
|------|------|------|
| 1 | 基准验证 | 融合日志完整，结构正常 |
| 2 | 新 Skill 解析 | data-exporter 提供 4 种导出格式 |
| 3 | 增量关系分析 | 与基准"可视化模块"部分重叠（都输出图表），但导出格式是新增能力 |
| - | 边界影响评估 | 导出能力不跨越清洗/可视化模块边界，可独立为第三模块 |
| 4 | 冲突检测 | 1 个中级别冲突：两者都生成图表输出，但方式不同（可视化=交互式，导出=静态文件） |
| - | 冲突解决 | 条件分支：交互式查看用可视化模块，文件导出用导出模块 |

### 融合结果: `data-pipeline`（扩展版）

```yaml
---
name: data-pipeline
description: >
  端到端数据处理流水线：从原始数据到可视化图表和导出文件。
  自动执行数据清洗、转换、可视化和导出，支持多种图表类型和导出格式。
  当用户需要快速将原始数据转换为可分享的图表或导出文件时使用。
---
```

```markdown
# 数据流水线

## 快速开始

提供原始数据文件，自动完成清洗、可视化和导出：

```
原始数据 → [数据清洗] → [可视化/导出] → 输出
```

## 模块边界

- **数据清洗模块**（来自 data-cleaner）
  - 职责：处理缺失值、异常值、格式标准化
  - 边界：输出清洗后的结构化数据

- **可视化模块**（来自 data-visualizer）
  - 职责：生成交互式图表
  - 边界：接收清洗后的数据，输出交互式图表

- **导出模块**（来自 data-exporter）
  - 职责：将数据或图表导出为文件（CSV/Excel/JSON/PDF）
  - 边界：接收清洗后的数据或图表，输出静态文件

## 使用示例

### 场景 1：快速可视化（默认）
自动选择最佳图表类型，一键生成交互式图表。

### 场景 2：导出为文件
指定导出格式，将清洗后的数据或图表导出为文件。

### 场景 3：完整流水线
清洗 → 可视化预览 → 导出为指定格式。
```

```html
<!-- 融合日志
来源 Skills: data-cleaner, data-visualizer (原始), data-exporter (增量)
融合模式: full (原始) + incremental (增量)
已解决冲突:
- [中] 图表输出方式 → 条件分支：交互式用可视化模块，文件导出用导出模块 (增量决策)
保留能力: 全部
排除能力: 无
增量变更:
- 新增能力: CSV/Excel/JSON/PDF 导出 (来自 data-exporter)
- 新增参考: references/export-formats.md
- 新增模块: 导出模块
融合日期: 2024-01-15 (原始), 2024-03-10 (增量)
-->
```

**关键洞察**：增量融合在已有模块边界清晰时效果最好。新能力作为独立模块添加，不破坏已有结构。

## 示例 8: 预览模式

### 输入 Skill

| Skill | 描述 | 核心功能 |
|-------|------|----------|
| **markdown-writer** | Markdown 文档撰写 | 生成结构化 Markdown 文档 |
| **code-reviewer** | 代码审查 | 审查代码质量、安全性和最佳实践 |

### 预览分析过程

| 阶段 | 操作 | 结果 |
|------|------|------|
| 1 | 收集验证 | 两个 Skill 均有效 |
| 2 | 深度解析 | A 处理文档生成，B 处理代码分析 |
| 3 | 关系分析 | 交叉度低（<10%），领域差异大 |

### 预览报告输出

```markdown
# 融合分析报告

## 基本信息

| 项目 | 内容 |
|------|------|
| 分析日期 | 2024-04-01 |
| 输入 Skill | markdown-writer, code-reviewer |
| 分析模式 | preview |

## 能力画像

### markdown-writer
- **核心能力**: Markdown 文档生成、格式化、模板应用
- **领域标签**: 文档、内容创作
- **触发条件**: 撰写文档、生成 README、创建技术文档
- **依赖项**: 无
- **复杂度**: 简单

### code-reviewer
- **核心能力**: 代码质量审查、安全漏洞检测、最佳实践建议
- **领域标签**: 代码质量、安全
- **触发条件**: 审查代码、代码评审、安全检查
- **依赖项**: 无
- **复杂度**: 中等

## 交叉度分析

| 维度 | 分析结果 |
|------|----------|
| 功能重叠百分比 | ~5% |
| 交叉度级别 | 低 |
| 重叠能力 | 两者都可能输出 Markdown 格式结果 |
| 重叠类型 | adjacent |

## 互补性分析

| 互补类型 | 具体内容 |
|----------|----------|
| 独特能力 | A 独有: 文档生成、模板; B 独有: 代码分析、安全检测 |
| 自然流水线 | B 的审查结果可由 A 格式化为文档 |
| 协同效应 | 代码审查报告的自动文档化 |

## 冲突检测

| 编号 | 严重级别 | 冲突描述 | 涉及 Skill | 建议解决策略 |
|------|----------|----------|------------|--------------|
| 1 | 低 | 两者都定义了 Markdown 输出格式 | A vs B | 自动去重 |

**冲突统计**: 严重 0, 高 0, 中 0, 低 1

## 低交叉度深度分析

### 场景串联机会
中等 — 代码审查 → 生成审查报告文档是一个合理的工作流，但用户也可以分别使用。

### 能力互补机会
中等 — B 产出审查结果，A 可以美化输出格式，但 B 本身已能输出 Markdown。

### 用户体验提升机会
低 — 合并后的便利性有限，用户通常在不同场景下使用两者。

### 融合方向建议

| 策略 | 适用性 | 预期效果 |
|------|--------|----------|
| 深度整合 | 低 | 过度耦合，两个独立场景被强制关联 |
| 轻量整合 | 中 | 可形成"审查+报告"工作流，但使用频率不高 |
| 编排整合 | 中 | 主 Skill 按需调用子 Skill，灵活但增加复杂度 |
| 不融合 | 高 | 两个 Skill 各自独立，各自场景清晰 |

### 最终建议

**建议不融合**。两个 Skill 属于不同领域，用户使用场景差异大。虽然存在"代码审查 → 生成报告"的串联场景，但频率不高，不足以支撑融合。保持独立更利于各自演进。

## 下一步建议

- 保持两个 Skill 独立
- 如需"代码审查报告"功能，可在 code-reviewer 中增加格式化输出选项
- 不推荐融合
```

**关键洞察**：预览模式的价值在于避免不必要的融合。不是所有"可以串联"的 Skill 都"应该融合"，使用频率和用户场景才是关键判断依据。

## 何时融合 vs 何时保持独立

### 应该融合

- ✅ Skill 属于相同或相邻领域
- ✅ Skill 有互补功能（A 的输出是 B 的输入）
- ✅ Skill 有重叠功能但不同实现（可统一）
- ✅ 用户经常同时使用这些 Skill

### 应该保持独立

- ❌ Skill 属于完全不相关的领域
- ❌ 融合后 Skill 将过于复杂（>3 个不同领域）
- ❌ 无共享知识或工作流可合并
- ❌ 用户很少同时使用这些 Skill
