# 融合算法

## 概述

融合算法通过六阶段流水线将多个独立的 Skill 转换为单一、连贯的新 Skill。每个阶段建立在前一阶段之上，确保系统化分析和结构化整合。

## 流水线阶段详解

### 阶段 1: 内容提取与解析

**目标**：深度解析每个 Skill 的完整文件结构。

对每个输入 Skill：

| 步骤 | 操作 | 输出 |
|------|------|------|
| 1.1 | 解析 SKILL.md frontmatter — 提取 `name`、`description` 和隐式元数据（触发模式、领域标签） | frontmatter 对象 |
| 1.2 | 解析 SKILL.md body — 分解为语义块 | 语义块列表 |
| 1.3 | 清点捆绑资源 | 资源清单 |

**语义块分类**：
- 工作流步骤 / 程序指令
- 工具使用指令
- 领域知识 / 参考内容
- 约束和规则
- 示例和边界情况

**资源清点**：
- `scripts/` — 列出每个脚本、用途、依赖和输入输出接口
- `references/` — 列出每个文件、主题范围和关键章节
- `assets/` — 列出每个资源、格式和使用场景

**输出**：每个 Skill 的结构化内容映射，按键值对形式组织（语义类别 → 内容）。

---

### 阶段 2: 语义分析与分类

**目标**：在功能层面理解每个 Skill 的作用。

对每个已解析的 Skill：

| 步骤 | 操作 | 输出 |
|------|------|------|
| 2.1 | 识别核心能力 — Skill 实现的主要动作 | 能力列表 |
| 2.2 | 提取领域标签 — 分类 Skill 的领域 | 领域标签 |
| 2.3 | 映射触发条件 — 何时为何调用此 Skill | 触发条件 |
| 2.4 | 识别依赖项 — 外部工具、API、文件格式 | 依赖清单 |
| 2.5 | 评估复杂度 — 简单/中等/复杂 | 复杂度评级 |

**复杂度评级标准**：
- **简单**：单一工作流
- **中等**：多个带条件的工作流
- **复杂**：多领域带分支逻辑

**输出**：每个 Skill 的能力画像。

---

### 阶段 3: 跨 Skill 关系分析

**目标**：发现 Skill 之间的关系 — 重叠、缺口和协同效应。

执行成对和组级分析：

| 分析维度 | 操作 | 输出 |
|----------|------|------|
| 功能重叠检测 | 比较能力画像找出共享或相似功能 | 重叠分类 |
| 互补性分析 | 识别独特能力、自然流水线、协同组合 | 互补性映射 |
| 依赖冲突检测 | 不兼容工具、矛盾指令、互斥约束 | 冲突清单 |
| 缺口分析 | 融合 Skill 应解决的缺失能力 | 缺口清单 |

**重叠严重度分类**：
- `identical`（完全相同）：相同功能，相同方法
- `equivalent`（等效）：相同功能，不同方法
- `adjacent`（相邻）：相关但不同的功能

**输出**：记录所有重叠、互补、冲突和缺口的关系矩阵。

---

### 阶段 4: 结构融合设计

**目标**：在编写任何内容前设计融合 Skill 的架构。

| 设计项 | 决策内容 |
|--------|----------|
| 范围 | 合并领域标签为统一范围；确定单领域（深度）或多领域（广度） |
| SKILL.md 结构 | 合并 frontmatter；设计 body 章节（渐进式披露） |
| 资源整合 | scripts/references/assets 的合并策略 |

**SKILL.md 结构设计**：
- **Frontmatter**：将 `name` 合并为复合名称，合成覆盖所有触发场景的 `description`
- **Body**：
  - 核心工作流（合并所有 Skill 的主要工作流）
  - 条件分支（保留每个 Skill 的变体逻辑）
  - 领域特定章节（多领域时按领域组织）

**资源整合策略**：
- `scripts/`：合并兼容脚本，标记冲突，弃用冗余脚本
- `references/`：按主题合并，去重，按领域重新组织
- `assets/`：合并所有资源，用命名空间前缀解决命名冲突

**输出**：融合蓝图 — 融合 Skill 的架构计划。

---

### 阶段 5: 内容合成

**目标**：基于蓝图生成实际的融合 Skill 内容。

| 合成项 | 操作 |
|--------|------|
| SKILL.md | 编写 frontmatter 和 body；整合工作流；合并领域知识；保留最佳示例 |
| 资源 | 按主题合并参考文件；整合脚本；组织资源 |
| 元数据 | 记录融合来源、冲突解决、排除的能力 |

**融合元数据格式**（嵌入 SKILL.md 的 HTML 注释）：
```html
<!-- 融合日志
来源 Skills: skill-a, skill-b, skill-c
已解决冲突:
- [严重] PDF 提取方法 → 用户选择 pdfplumber
- [高] 图片调整算法 → 合并：照片用双线性，像素画用最近邻
保留能力: 全部
排除能力: 无
融合日期: 2024-01-15
-->
```

**输出**：完整的融合 Skill 目录。

---

### 阶段 6: 验证与优化

**目标**：确保融合 Skill 正确、完整且可用。

| 验证类型 | 检查项 |
|----------|--------|
| 结构验证 | frontmatter 格式、资源引用有效性、渐进式披露正确实现 |
| 内容验证 | 无能力被静默丢弃、无内部矛盾、示例准确、脚本依赖完整解析 |
| 可用性优化 | SKILL.md 行数 ≤ `max_body_lines`（默认 500，可配置）、描述正确触发、不过度复杂 |

**复杂度检查**：如果融合 Skill 涉及 > 配置项 `max_complex_domains`（默认 3 个）不同领域，考虑拆分为多个 Skill。上述阈值的默认值与覆盖机制见 [fusion-config.md](fusion-config.md)。

**输出**：验证通过、优化后的融合 Skill。

## 算法特性

| 特性 | 说明 |
|------|------|
| **组合性** | 每个阶段产生明确定义的产物，输入到下一阶段 |
| **交互性** | 阶段 3-5 的冲突解决需要用户参与 |
| **可追溯性** | 每个合并决策都记录在融合日志中 |
| **非破坏性** | 原始 Skill 保持不变；融合 Skill 是新产物 |

## 阶段依赖关系

```
阶段 1 (提取) → 阶段 2 (分析) → 阶段 3 (关系) → 阶段 4 (设计) → 阶段 5 (合成) → 阶段 6 (验证)
     │               │               │               │               │               │
     └───────────────┴───────────────┴───────────────┴───────────────┴───────────────┘
                              用户交互点（冲突解决）
```

**注意**：阶段 1-2 可自动化；阶段 3-5 需要用户参与决策；阶段 6 为最终验证。

## 低交叉度 Skill 的智能融合策略

当输入 Skill 之间的功能交叉度较低时，不应强行合并，而应采用**深度理解 + 寻找融合价值点**的策略。

### 交叉度评估标准

| 交叉度级别 | 特征 | 融合策略 |
|------------|------|----------|
| **高交叉度** | 功能重叠 ≥ `overlap_high`（默认 50%），或存在自然流水线关系 | 直接融合，合并重叠部分 |
| **中交叉度** | 功能重叠 ∈ [`overlap_mid`, `overlap_high`)（默认 20-50%），存在互补场景 | 智能整合，保留特色能力 |
| **低交叉度** | 功能重叠 < `overlap_mid`（默认 20%），领域差异大 | 深度分析后决定是否融合 |

> 交叉度阈值（`overlap_high` / `overlap_mid`）与其它规则阈值均为可配置项，默认值与覆盖机制参见 [fusion-config.md](fusion-config.md)。

### 低交叉度处理流程

当检测到交叉度较低时，进入**扩展分析流程**：

#### 步骤 A：深度语义理解

不仅分析"做什么"，更要理解"为什么做"和"为谁做"：

| 分析维度 | 关键问题 | 分析目标 |
|----------|----------|----------|
| **用户意图** | 这个 Skill 解决什么用户痛点？ | 理解核心价值主张 |
| **使用场景** | 在什么上下文被调用？ | 发现潜在的协同场景 |
| **能力边界** | 明确不做什么？ | 识别能力缺口和扩展点 |
| **演进方向** | 未来可能扩展什么功能？ | 预判融合的长期价值 |

#### 步骤 B：寻找融合价值点

即使功能交叉度低，也可能存在以下融合价值：

**1. 场景串联价值**
```
示例：
- Skill A: 数据清洗（数据处理领域）
- Skill B: 数据可视化（图表展示领域）
- 交叉度：低（功能完全不同）
- 融合价值：高（形成完整的数据分析工作流）
```

**2. 能力互补价值**
```
示例：
- Skill A: 前端组件开发（React）
- Skill B: 组件测试（Jest）
- 交叉度：低（开发 vs 测试）
- 融合价值：高（开发+测试的完整组件工作流）
```

**3. 知识复用价值**
```
示例：
- Skill A: Python 数据分析
- Skill B: Python 机器学习
- 交叉度：中（都使用 Python，但应用场景不同）
- 融合价值：中（共享 Python 环境配置、依赖管理等知识）
```

**4. 用户体验价值**
```
示例：
- Skill A: 文档生成（Markdown）
- Skill B: 文档发布（GitHub Pages）
- 交叉度：低（生成 vs 发布）
- 融合价值：高（一键生成并发布，提升用户体验）
```

#### 步骤 C：融合方向决策

基于深度分析，选择以下四种策略之一：

| 策略 | 适用场景 | 输出形式 |
|------|----------|----------|
| **深度整合** | 发现强协同价值 | 单一融合 Skill，形成连贯工作流 |
| **轻量整合** | 发现弱协同价值 | 融合 Skill + 清晰的模块边界 |
| **编排整合** | 无直接协同但需顺序执行 | 主 Skill 调用多个子 Skill 的编排模式 |
| **建议不融合** | 无协同价值，强行融合有害 | 输出分析报告，建议保持独立 |

#### 步骤 D：优化输出设计

对于决定融合的情况，优化输出结构：

**1. 模块化架构**
```
<融合-skill>/
├── SKILL.md                 # 主入口，说明整体工作流
├── references/
│   ├── module-a/            # Skill A 的能力模块
│   │   └── ...
│   ├── module-b/            # Skill B 的能力模块
│   │   └── ...
│   └── integration.md       # 模块整合指南
└── scripts/
    ├── module-a/            # Skill A 的脚本
    └── module-b/            # Skill B 的脚本
```

**2. 渐进式引导**
- **第一层**：快速开始 — 最常见的整合使用方式
- **第二层**：模块指南 — 各模块的独立使用说明
- **第三层**：高级整合 — 复杂的跨模块场景

**3. 清晰的边界定义**
在 SKILL.md 中明确标注：
```markdown
## 模块边界

- **数据清洗模块**（来自 skill-data-cleaner）
  - 职责：清洗和预处理原始数据
  - 边界：输出清洗后的数据，不处理可视化

- **可视化模块**（来自 skill-data-viz）
  - 职责：将清洗后的数据转换为图表
  - 边界：接收清洗后的数据，不处理原始数据
```

### 用户交互流程

当检测到低交叉度时，向用户展示：

```markdown
## 交叉度分析报告

**检测到的 Skill**：
- Skill A: [名称] — [核心能力]
- Skill B: [名称] — [核心能力]

**交叉度评估**：低（功能重叠约 X%）

**深度分析发现**：
1. **场景串联机会**：[描述]
2. **能力互补机会**：[描述]
3. **潜在风险**：[强行融合可能导致的问题]

**建议策略**：[深度整合/轻量整合/编排整合/建议不融合]

**理由**：[详细说明]

是否按建议策略继续？（是/否/调整策略）
```

### 反模式警示

以下情况**不应强行融合**：

| 反模式 | 特征 | 后果 |
|--------|------|------|
| **大杂烩** | 将无关功能硬塞进一个 Skill | 用户困惑，难以定位功能 |
| **领域混淆** | 数据库操作 + 图片编辑 | 违反单一职责原则 |
| **复杂度爆炸** | 融合后 Skill 涉及 > 配置项 `max_anti_pattern_domains`（默认 5 个）领域 | 维护困难，学习成本高 |
| **能力稀释** | 为了融合而删减核心能力 | 失去原有 Skill 的优势 |
