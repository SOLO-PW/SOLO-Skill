# 输出模板

## 概述

本文档定义融合后 Skill 的标准输出结构，确保输出一致性和质量。

## 目录结构模板

### 基础结构（无脚本和资源）

```
<融合-skill-名称>/
├── SKILL.md
└── references/
    ├── <主题1>.md
    └── <主题2>.md
```

### 完整结构（含脚本和资源）

```
<融合-skill-名称>/
├── SKILL.md
├── scripts/
│   ├── <命名空间>-<功能>.py
│   └── <命名空间>-<功能>.py
├── references/
│   ├── <主题1>.md
│   ├── <主题2>.md
│   └── integration.md     # 多模块时的整合指南
└── assets/
    ├── <命名空间>-<资源>.<ext>
    └── <命名空间>-<资源>.<ext>
```

## SKILL.md 模板

```markdown
---
name: <融合-skill-名称>
description: >
  <一句话概括融合后的核心能力>。
  <列出主要功能和触发场景>。
  当用户需要<触发场景1>、<触发场景2>或<触发场景3>时使用。
---

# <融合 Skill 标题>

<1-2 句话说明这个 Skill 做什么>

---

## 快速开始

<最常见的使用方式，3 步以内>

## 工作流

### <主工作流名称>

1. **<步骤1>** — <简要说明>
2. **<步骤2>** — <简要说明>
3. **<步骤3>** — <简要说明>

### <条件分支（如需要）>

- **<条件A>**：<处理方式>
- **<条件B>**：<处理方式>

## 模块边界（低交叉度融合时）

- **<模块A名称>**（来自 <源Skill名称>）
  - 职责：<描述>
  - 边界：<明确不做什么>

- **<模块B名称>**（来自 <源Skill名称>）
  - 职责：<描述>
  - 边界：<明确不做什么>

## 参考

- **<主题1>**：[references/<文件名>.md](references/<文件名>.md) — <简要说明>
- **<主题2>**：[references/<文件名>.md](references/<文件名>.md) — <简要说明>

<!-- 融合日志
来源 Skills: <skill-a>, <skill-b>
融合模式: <full/incremental>
已解决冲突:
- [<级别>] <冲突描述> → <解决方案>
保留能力: <全部/列出排除项>
排除能力: <无/列出排除项及原因>
融合日期: <日期>
-->
```

## 融合日志规范

融合日志以 HTML 注释形式嵌入 SKILL.md 末尾，确保可追溯性。

### 字段说明

| 字段 | 必需 | 说明 |
|------|------|------|
| 来源 Skills | 是 | 所有源 Skill 名称，按提供顺序 |
| 融合模式 | 是 | `full` 或 `incremental`（增量时标注原始+增量） |
| 已解决冲突 | 是 | 每个冲突的级别、描述和解决方案 |
| 保留能力 | 是 | `全部` 或列出被保留的能力 |
| 排除能力 | 是 | `无` 或列出被排除的能力及原因 |
| 融合日期 | 是 | ISO 8601 格式 |

### 融合日志完整性校验

每次生成（full）或追加（incremental）融合日志后，必须通过以下校验：

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 注释存在 | 以 `<!-- 融合日志` 开头，以 `-->` 正确闭合 |
| 2 | 必需字段齐全 | 上表 6 个必需字段均已填写 |
| 3 | 字段值有效 | 融合模式在 `full`/`incremental`（增量含原始+增量标注）内；日期为 ISO 8601 |
| 4 | 冲突记录完整 | 每个已解决冲突含级别、描述、解决方案 |
| 5 | 增量变更已并表 | 增量模式在追加 `增量变更:` 条目后，仍满足上表全部字段（追加不破坏原始字段） |

**生效范围**：该校验对 **full 与 incremental 两种模式都强制生效**。增量融合时，基准融合日志在增量前已通过校验；追加增量变更后需再次运行本清单，确保字段完整性与注释闭合性不被破坏。具体调用点：

- full 模式：见 SKILL.md 步骤 6 必过项「融合日志已嵌入」
- incremental 模式：见 [incremental-fusion.md](incremental-fusion.md) 步骤 1 基准验证与步骤 6 增量验证

### 增量融合日志

```html
<!-- 融合日志
来源 Skills: <skill-a>, <skill-b> (原始), <skill-c> (增量)
融合模式: full (原始) + incremental (增量)
已解决冲突:
- [<级别>] <冲突描述> → <解决方案> (原始决策)
- [<级别>] <冲突描述> → <解决方案> (增量决策)
保留能力: 全部
排除能力: 无
增量变更:
- 新增能力: <能力描述> (来自 <skill-c>)
- 新增参考: references/<文件名>
- 修改模块: <模块名> (<变更说明>)
融合日期: <原始日期> (原始), <增量日期> (增量)
-->
```

## 命名规范

### Skill 名称

- 使用小写字母、数字和连字符
- 动词-名词结构优先（如 `pdf-to-structured-data`）
- 反映融合后的核心能力，非源 Skill 的简单拼接
- 长度 ≤ 配置项 `max_skill_name_len`（默认 64 字符，可配置，见 [fusion-config.md](fusion-config.md)）

### 脚本命名

- 格式：`<命名空间>-<功能>.<ext>`
- 命名空间使用源 Skill 名称或模块名称
- 示例：`pdf-extract-text.py`、`data-format-csv.py`

> 多 Skill 脚本合并时的依赖解析与冲突检测遵循 [script-dependency-check.md](script-dependency-check.md)。

### 参考文件命名

- 使用小写字母和连字符
- 反映文件主题
- 示例：`pdfplumber-guide.md`、`format-specs.md`

### 资源命名

- 格式：`<命名空间>-<描述>.<ext>`
- 避免通用名称（如 `logo.png` → `brand-logo.png`）

## 参考文件合并策略

### 无重叠

直接保留两个文件，无需处理。

### 部分重叠

合并为一个文件，按主题分章节：

```markdown
# <合并主题>

## <Skill A 视角>

<Skill A 的内容>

## <Skill B 视角>

<Skill B 的内容>
```

### 高度重叠

保留更全面的版本，将另一版本的独有细节补充进去。

### 矛盾内容

不自动合并，标记为冲突，按冲突解决流程处理。
